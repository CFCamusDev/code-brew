# Release 1.1.0

Candidato preparado a partir de `develop` actualizado en `a95117b` (merge de `main` a `develop`, PR #23). Incorpora las novedades de tienda, video y equipos, conservando las correcciones de seguridad de 1.0.0.

## Correcciones para Portainer

- La aplicación valida su configuración antes de aplicar migraciones: contraseña de ejemplo, URL de base inválida, llaves Culqi incompletas o mezcladas, webhook ausente con pagos habilitados y configuración incompleta de correo.
- Webhook sin `CULQI_WEBHOOK_SECRET`: responde 503 y no procesa eventos.
- App y Nginx tienen healthchecks. Compose espera a PostgreSQL saludable antes de iniciar la app y a la app saludable antes de iniciar Nginx.
- Nginx vuelve a resolver el servicio con el DNS de Docker para evitar que conserve una IP antigua tras recrear la app. Conserva el Host y el protocolo original del proxy HTTPS.
- El proceso Node recibe directamente SIGTERM para detener el contenedor.
- `/api/health` indica `version: "1.1.0"` y envía `Cache-Control: no-store`.

## Variables de la stack

El `.env` compartido para la revisión necesita estos ajustes antes de desplegar:

| Variable | Configuración |
| --- | --- |
| `POSTGRES_PASSWORD` | Sustituir la contraseña de ejemplo por una aleatoria alfanumérica de al menos 32 caracteres. |
| `CULQI_PUBLIC_KEY`, `CULQI_SECRET_KEY` | Llaves del mismo entorno. Las de prueba no equivalen a pagos reales. Rotar las claves compartidas y cargarlas únicamente en Portainer. |
| `CULQI_WEBHOOK_SECRET` | Falta en el ejemplo compartido. Obligatoria con Culqi habilitado, mínimo 32 caracteres aleatorios. Registrar el webhook con `?key=...`. |
| `CRON_SECRET` | Configurar mínimo 32 caracteres si se desean cancelar pedidos abandonados. Debe coincidir con el secreto de GitHub Actions. Sin ella, el cron responde 503. |
| `RESEND_API_KEY` | Rotar la clave compartida y cargarla en Portainer; las pruebas automatizadas no envían correo. |
| `EMAIL_FROM` | Remitente de un dominio verificado en Resend. |
| `SITE_URL` | `https://coffeecodebrew.com`, sin rutas. |
| `ADMIN_EMAIL` | Correo que recibirá los avisos administrativos. |
| `PORT` | `8025` es el puerto público del proxy; la app usa internamente 4321. |
| `DATABASE_URL` | La URL con `localhost:5434` es solo para desarrollo. Compose construye su propia URL interna con `codebrew-db:5432`; no hay que copiar la URL local a la app de producción. |
| `PUBLIC_ANALYTICS_ENV` | `production` para activar GA4; por defecto está desactivada. Es una variable de compilación. |

Generar cada secreto por separado: `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`. No guardar secretos en commits ni imágenes.

Si ya existe un volumen de PostgreSQL, modificar `POSTGRES_PASSWORD` en Portainer no cambia la contraseña del usuario existente. Coordinar primero el cambio en PostgreSQL y luego actualizar la stack con el mismo valor. Respaldar la base antes de hacerlo; no borrar el volumen para resolver un error de autenticación.

## Despliegue

Esta configuración está diseñada para **Docker Standalone con Compose**. En Portainer usar una stack desde Git, el repositorio completo y `docker-compose.yml` como Compose path. El editor de YAML por sí solo no contiene el Dockerfile ni el código. En producción usar `refs/heads/main` después de fusionar el PR; para probar el candidato usar `refs/heads/release/1.1.0` en un entorno separado.

Docker Swarm no construye los servicios con `build:`: requiere publicar imágenes y preparar una configuración específica. No usar esta stack como si fuese una definición Swarm.

1. Respaldar PostgreSQL y cargar las variables en Portainer.
2. Fusionar el release con CI aprobado y reconstruir la stack.
3. Verificar los tres contenedores saludables, la versión en `/api/health` y el acceso HTTPS al panel.
4. Confirmar catálogo, precios, inventario y tarifas.
5. Probar pagos/webhooks Culqi y correos de Resend con las cuentas del comercio en un entorno de pruebas.
6. Etiquetar el commit fusionado como `v1.1.0` y sincronizar los ajustes de vuelta a `develop`.

Las migraciones y el seed se ejecutan al arrancar. El seed conserva precios, stock y tarifas editados. Revertir la imagen no revierte migraciones: recuperar una base incompatible requiere su respaldo.

## Pruebas reproducibles

`pnpm test:docker` requiere Docker Compose >= 2.24.4. Levanta la misma stack con un proyecto único, PostgreSQL desechable, puertos locales aleatorios y credenciales generadas para QA. Ejecuta tipos, pruebas unitarias, comprobación de migraciones e integración pasando por Nginx. Al terminar elimina únicamente su proyecto y volúmenes. No lee el `.env` local ni utiliza llaves reales. `pnpm test:docker --keep` conserva los contenedores para diagnóstico.

Además se probaron en QA la recreación de la app con otra IP sin reiniciar Nginx, la conservación de precio/stock al repetir migraciones y seed, el rechazo de la configuración incompleta y el HTTP 503 del webhook sin secreto.

Resultado del candidato 1.1.0 (2026-10-26): build de las imágenes, tipos y comprobación de migraciones correctos; 44 pruebas unitarias y 47 de integración aprobadas. La prueba condicional del webhook sin secreto se omite en la suite con secreto configurado y se comprobó aparte con HTTP 503. También se verificaron cookies Secure/HttpOnly al reenviar HTTPS, reconexión después de reiniciar PostgreSQL y ausencia del `.env` en la imagen. La ejecución final de `pnpm test:docker` terminó con código 0 y limpió su stack y volumen desechable.

La auditoría del lockfile no reportó vulnerabilidades conocidas en la consulta del 2026-10-26. Se mantiene el aviso de chunks JavaScript superiores a 500 kB. Las pruebas no certifican la conectividad de las cuentas Culqi/Resend ni sustituyen una revisión visual móvil; tampoco se accedió al Portainer o a la base de producción.

Referencias: [variables y stacks en Portainer](https://docs.portainer.io/user/docker/stacks/add), [orden de arranque y salud en Compose](https://docs.docker.com/compose/how-tos/startup-order/).
