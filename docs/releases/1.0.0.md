# Release 1.0.0

Primera versión 1.x de CodeBrew. Rama `release/1.0.0`, creada desde `develop` en `7d0d69d`. El PR se dirige a `main`; la etiqueta `v1.0.0` se crea después de fusionarlo y comprobar el despliegue.

## Alcance

- Tienda con carrito, checkout, pedidos y seguimiento por correo y número de pedido.
- Pagos Culqi, confirmación por webhook y alternativa por WhatsApp.
- Panel de administración con roles, inventario, envíos, gastos, exportaciones y métricas.
- Analítica GA4 habilitada solo explícitamente en producción.
- Preparación de seguridad: actualización de Astro, adaptadores, Sharp y Vitest; dependencias directas fijadas y lockfile versionado.

## Entorno

- Node 22.23.4 y pnpm 10.30.3; Docker y CI usan el mismo runtime.
- Instalar con `pnpm install --frozen-lockfile`. No regenerar el lockfile en el despliegue.
- Los overrides de Undici 8.12.2 y esbuild 0.25.12 corrigen avisos transitivos de seguridad. Revisarlos cuando sus dependencias padre incorporen las correcciones.
- Copiar `.env.example` a `.env` para desarrollo. No subir credenciales.
- `DATABASE_URL` de ejemplo corresponde únicamente a PostgreSQL local en el puerto 5434.
- En producción, Compose construye `DATABASE_URL` usando `POSTGRES_PASSWORD`. Usar una contraseña aleatoria alfanumérica de al menos 32 caracteres para evitar caracteres reservados en la URL.
- `SITE_URL` debe ser el dominio HTTPS público, sin rutas, para los enlaces de correo. En local debe coincidir con el puerto real de Astro.
- Las llaves Culqi quedan vacías por defecto. Para cobros reales, configurar ambas llaves del mismo entorno y `CULQI_WEBHOOK_SECRET`; registrar el webhook HTTPS y probarlo en modo de pruebas antes de usar llaves live.
- Configurar `RESEND_API_KEY`, `EMAIL_FROM` de un dominio verificado y `ADMIN_EMAIL` para los correos.
- Generar `CRON_SECRET` y `CULQI_WEBHOOK_SECRET` diferentes y aleatorios con `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"`.
- Configurar `CRON_SECRET` también en GitHub. `PUBLIC_ANALYTICS_ENV` y `PUBLIC_GA4_ID` se incorporan al compilar y requieren reconstruir la imagen cuando cambian.
- Las pruebas de integración usan `INTEGRATION_BASE_URL` y una base de datos desechable; modifican inventario y crean usuarios. Nunca apuntarlas a producción.

## Antes de fusionar

1. Revisar los resultados de CI: tipos, pruebas unitarias, integración y construcción de las dos imágenes Docker.
2. Comprobar carrito, checkout, acceso al panel y seguimiento en un entorno de pruebas.
3. Probar un pago y su webhook con Culqi de pruebas, incluido un reintento, y comprobar un correo con Resend.
4. Confirmar precios, stock, tarifas de envío, dominio HTTPS y variables reales de la stack.
5. Respaldar PostgreSQL antes del despliegue: el arranque aplica migraciones automáticamente.

## Validación local del candidato (2026-10-23)

- Instalación con lockfile congelado: correcta.
- `pnpm audit` y `pnpm audit --prod`: sin vulnerabilidades conocidas en la consulta de preparación.
- `pnpm typecheck`: correcto.
- Pruebas unitarias: 34 aprobadas.
- Pruebas de integración: 45 aprobadas contra el servidor compilado y repetidas correctamente contra las imágenes Docker a través de Nginx.
- PostgreSQL desechable: migraciones, seed y `drizzle-kit check` correctos. No se modificó la base de producción.
- Imágenes Docker `runner` y `web`: construidas; Nginx validado en la red aislada.
- Arranque del contenedor como usuario `node`, migraciones automáticas, landing HTTP 200 y `/api/health` con base de datos OK.
- Compose validado sin imprimir secretos. El `.env` local no se modificó ni se incluyó en las imágenes.

La compilación conserva un aviso de chunks JavaScript superiores a 500 kB; no impide el build. Quedan pendientes las comprobaciones visuales y los pagos, webhooks y correos con las cuentas reales del comercio en un entorno de pruebas. Las pruebas automatizadas no realizan cobros ni envían correos reales.

Se consultaron las guías oficiales de migración de [Astro 6](https://docs.astro.build/en/guides/upgrade-to/v6/) y [Astro 7](https://docs.astro.build/en/guides/upgrade-to/v7/). Se mantiene `compressHTML: true` explícito para conservar el tratamiento previo de espacios al migrar. La numeración sigue la convención de [primera versión 1.0.0 de npm](https://docs.npmjs.com/about-semantic-versioning/).

## Despliegue y recuperación

Después de fusionar, CI activa el workflow de despliegue si está configurado `PORTAINER_WEBHOOK_URL`. Comprobar `/api/health`, crear el primer administrador con `pnpm admin:create` si hace falta y revisar los logs. Etiquetar el commit fusionado como `v1.0.0` y sincronizar los ajustes del release de vuelta a `develop`.

Para recuperar la aplicación, desplegar la imagen/commit anterior. Esto no revierte las migraciones: si existe incompatibilidad de esquema, restaurar el respaldo de PostgreSQL en una ventana de mantenimiento.
